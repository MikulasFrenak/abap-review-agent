### [High] SELECT inside a loop
- File: `fixtures/z_review_fixture_01_select_in_loop.abap:13`
- Pattern: SELECT inside a loop
- Why: `SELECT * FROM vbap ... WHERE vbeln = ls_order-vbeln` runs once per iteration of `LOOP AT lt_orders`, i.e. once per order — classic N+1. If `lt_orders` holds real order volumes, this is one database round-trip per order instead of one for the whole batch.
- Suggested direction: hoist the SELECT out of the loop, batch with `SELECT ... FOR ALL ENTRIES IN lt_orders` (guarded — see next finding), or a JOIN if the shape allows.

### [High] Missing FOR ALL ENTRIES guard
- File: `fixtures/z_review_fixture_02_missing_for_all_entries_guard.abap:11`
- Pattern: Missing FOR ALL ENTRIES guard
- Why: `SELECT ... FOR ALL ENTRIES IN lt_keys` has no `IF lt_keys IS NOT INITIAL` (or equivalent) guard before it. If `lt_keys` is empty at runtime, ABAP drops the implicit WHERE restriction and this selects every row of VBAP — a correctness bug, not just a slow query.
- Suggested direction: wrap the SELECT in an emptiness check on `lt_keys`; skip the SELECT entirely (and clear the target table) when there's nothing to look up.

### [High] Nested SELECT ... ENDSELECT
- File: `fixtures/z_review_fixture_03_nested_select.abap:12`
- Pattern: Nested SELECTs
- Why: The outer `SELECT * FROM vbak ... ENDSELECT` (line 11) is already a row-by-row database loop; the inner `SELECT * FROM vbap` on line 12 compounds it, so total DB round-trips scale with the outer result set size. Worse than fixture 01, same root cause.
- Suggested direction: replace both loops with a single set-based read — one SELECT (or JOIN) that returns everything needed, processed in ABAP afterward.

### [Medium] Nested LOOP AT over two internal tables
- File: `fixtures/z_review_fixture_04_internal_table_antipatterns.abap:16`
- Pattern: Internal table anti-pattern
- Why: `LOOP AT lt_materials` containing `LOOP AT lt_plants WHERE matnr = ...` is O(n×m) — for every material, the full `lt_plants` table is scanned linearly. Fine for small tables, real cost if both tables hold production-scale data.
- Suggested direction: if `lt_plants` doesn't need to stay a `STANDARD TABLE`, switch it to `SORTED`/`HASHED` with a key on `matnr` and use `READ TABLE ... WITH [TABLE] KEY` instead of a nested loop.

### [Medium] Linear READ TABLE without BINARY SEARCH or a keyed table type
- File: `fixtures/z_review_fixture_04_internal_table_antipatterns.abap:20`
- Pattern: Internal table anti-pattern
- Why: `READ TABLE lt_plants ... WITH KEY matnr = ...` on a plain `STANDARD TABLE` inside the outer loop is a linear scan per iteration — O(n) per read, O(n×m) total across the loop.
- Suggested direction: same fix as the finding above — a `HASHED`/`SORTED` table with a unique key on `matnr` turns this into an O(1)/O(log n) lookup.
